=== SOLID principle

* ByteByteGo "What is the SOLID Principle?" : https://blog.bytebytego.com/p/ep175-what-is-the-solid-principle +
image:20250809_ByteByteGo_SOLID-principle_01.jpg[]

The SOLID acronym stands for:

	* S -> *Single Responsibility Principle*
		** The Single Responsibility Principle (SRP) states that a class should have only one reason to change. In other words, it should have a single, well-defined responsibility or task within a software system.
	* O -> *Open/Closed Principle*
		** The Open/Closed Principle (OCP) states that software entities, such as classes, should be open for extension but closed for modification. This means you can add new functionality without altering existing code.
	* L -> *Liskov Substitution Principle*
		** The Liskov Substitution Principle (LSP) states that objects of a derived class should be able to replace objects of the base class without affecting the correctness of the program.
	* I -> *Interface Segregation Principle*
		** The Interface Segregation Principle (ISP) emphasizes that classes or components that use interfaces should not be forced to depend on interfaces they don't use.
	* D -> *Dependency Inversion Principle*
		** The Dependency Inversion Principle (DIP) states that high-level modules (or classes) should not depend on low-level modules; both should depend on abstractions, such as interfaces.

=== Architecture microservices

* 2025/10/16 - ByteByteGo "Components of a Production-Ready Microservice Architecture" : https://blog.bytebytego.com/p/a-guide-to-microservices-architecture +
image:20251105_ByteByteGo_microservices_01.jpg[]

	1. *API Gateway*: As mentioned, the API Gateway acts as the front door to the system. It receives all client requests and routes them to the correct microservices. It can also filter requests, enforce security rules, and perform load balancing to spread traffic evenly across service instances.

	2. *Service Registry*: In a microservices environment, services often scale up or down dynamically. A service registry keeps track of available service instances and their locations. This allows other services or the gateway to discover them without relying on hardcoded addresses.

	3. *Service Layer*: This is where the actual business logic resides. Each service is built to handle a specific domain, such as orders, payments, or notifications. Frameworks make it easier to develop scalable services with built-in support for REST APIs, dependency injection, and testing.

	4. *Authorization Server*: Security is critical in distributed systems. An Authorization Server handles authentication and access control across all services. Instead of each service managing credentials, the server issues tokens that validate user identity and permissions.

	5. *Data Storage*: Each service typically manages its own database, which may be relational (PostgreSQL, MySQL) or non-relational (MongoDB, Cassandra). This separation reduces coupling and enables polyglot persistence, where teams choose the database that best fits their service's requirements.

	6. *Distributed Caching*: Caching improves performance by storing frequently accessed data in memory. Distributed caches can be shared across multiple service instances, reducing database load and speeding up response times.

	7. *Asynchronous Communication*: Synchronous calls like REST are simple, but they create dependencies. Asynchronous communication allows services to exchange information without waiting for immediate responses.

	8. *Metrics and Monitoring*: Observability is key to managing microservices. Services should publish metrics about their performance, error rates, and resource usage. Tools like Prometheus collect these metrics, while Grafana visualizes them in dashboards, enabling teams to detect issues quickly.

	9. *Centralized Logging*: Logs are essential for debugging, but in microservices, they are spread across many services. Centralized logging pipelines collect, store, and analyze logs in one place. A common setup is the ELK stack: Logstash to collect, Elasticsearch to store, and Kibana to visualize.

=== Qu'est-ce qu'un bon Software Architect ?

(Très bonne) réponse de Perplexity sur la base de l'article "What is good software architecture ?" de The Pragmatic Engineer : +
https://newsletter.pragmaticengineer.com/p/what-is-good-software-architecture

[source, markdown]
----
Un bon software architect, selon l'article, est quelqu'un qui sait surtout faire de *bons arbitrages de problèmes* dans le temps, aligner les gens autant que les systèmes, et proposer des architectures réalistes qui livrent de la valeur dans le monde tel qu'il est, pas dans un monde idéal.[1]

## Idée centrale : upgrader ses problèmes

- L'architecture n'est pas une quête de perfection mais un jeu de trade-offs : on échange des problèmes actuels contre des problèmes futurs, mais meilleurs (plus maîtrisables, plus créateurs de valeur business).[1]
- Si un « chantier d'architecture » consomme beaucoup d'énergie sans changer les contraintes structurantes (scalabilité, vitesse de delivery, fiabilité, coût…), c'est juste de la “re-décoration” de maison qui devrait être reconstruite.[1]

Exemple clé : la migration de Netflix vers AWS.  
- On a troqué un environnement on-prem stable mais rigide (capacité fixe, croissance limitée) pour un cloud élastique mais instable (instances défaillantes, réseau moins fiable, autoscaling complexe).[1]
- Cela a créé une multitude de nouveaux problèmes techniques (résilience, circuit breakers, discovery, autoscaling prédictif), mais ces problèmes étaient largement préférables à la limitation de croissance liée au datacenter.[1]

## Le rôle des architects remis en cause

- Chez Netflix, pendant longtemps, il n'y avait pas d'Architects au sens de titre de poste : les mêmes ingénieurs proposaient, implémentaient, opéraient, prenaient les astreintes.[1]
- Quand sont apparus des profils « Architectes » déconnectés du run (pas d'on-call, peu dans la boue opérationnelle), ils ont commencé à pousser de grands designs pour des problèmes hypothétiques, peu ancrés dans la réalité des équipes.[1]

L'auteur critique le modèle “waterfall” classique :  
- Design (architectes), Build (dev), Test (QA), Operate (Ops) comme silos séparés.[1]
- Avec Agile, DevOps et « you build it, you run it », les frontières se floutent et le rôle d'architecte « pur penseur » devient souvent contre-productif, car il se coupe des vrais feedback loops (incidents, limitations des systèmes, contraintes d'organisation).[1]

## Bon code vs bonne architecture

- La capacité à écrire du « beau code » est orthogonale à la capacité à concevoir une bonne architecture de systèmes distribués.[1]
- On peut être mauvais en code mais excellent pour poser les bonnes questions macros : SLA, latence acceptable, batch vs temps réel, résilience, données à tracer pour diagnostiquer.[1]

À l'inverse :  
- Être expert en détails de langage, patterns, micro-optimisations ne garantit absolument pas la capacité à assembler des services cohérents, robustes, évolutifs.[1]
- L'auteur insiste que l'architecture, c'est la manière dont les systèmes interagissent, au service du business, pas la qualité de chaque classe isolée.[1]

## Architecture comme travail social

- Un bon architecte ne relie pas seulement des services mais aussi des équipes, des intérêts, des agendas.[1]
- Sur un projet d'analytics de personnalisation dans un grand réseau social, l'auteur illustre qu'un bon design doc technique, seul, ne suffit pas : l'échec venait surtout d'un manque de vision partagée et d'alignement entre stakeholders.[1]

En pratique :  
- « Avoir raison techniquement » ne suffit pas si personne ne suit : un design est bon quand il met vraiment les gens en mouvement dans la même direction.[1]
- Le travail architectural consiste donc aussi à simplifier le problème, cadrer le vocabulaire, trancher les frontières fonctionnelles (ex : qu'est-ce qui est analytics ou non), et créer un narratif que les équipes adoptent.[1]

## Pratique vs aspirationnel

- L'auteur oppose deux mauvais extrêmes :  
  - Architecture trop pratique : plein de “petites” améliorations réalistes mais qui ne changent jamais la donne.[1]
  - Architecture trop aspirationnelle : grand dessin parfait, mais inatteignable dans l'organisation actuelle (nécessite reorg, réécriture totale, etc.).[1]

Exemple de perso vidéo ranking chez un opérateur TV US :  
- Le Search team est lent pour de bonnes raisons (stabilité, volume, change management). Le Personalization team est rapide pour de bonnes raisons (expérimentation, ML).[1]
- Proposer une architecture qui dépend lourdement d'évolutions côté Search est vain : même techniquement idéale, elle ne sera jamais livrée à temps. La “bonne” architecture tient compte des vitesses réelles des équipes et des contraintes politiques.[1]

L'approche préconisée :  
- Concevoir plusieurs architectures candidates, les prototyper avec du vrai trafic, privilégier celles qui maximisent la valeur sous contraintes existantes (org, ownership, cadence de delivery).[1]
- Utiliser le trafic de prod comme juge ultime entre options ambitieuses, plutôt que des débats abstraits.[1]

## Bon vs mauvais travail d'architecture (synthèse)

- Bon travail d'architecture :  
  - Change le type de problèmes rencontrés (scalabilité, vitesse de mise en prod, résilience, coût, flexibilité produit).[1]
  - Ancre les choix dans les contraintes réelles (cloud instable, équipes lentes/rapides, dette existante, maturité SRE/DevOps).[1]
  - Aligne les équipes autour d'une vision suffisamment simple pour être comprise, suffisamment ambitieuse pour que ça vaille l'effort.[1]

- Mauvais travail d'architecture :  
  - Produit beaucoup de docs, de décisions “propres”, de refactors locaux, mais n'améliore ni le débit, ni la fiabilité, ni la trajectoire business.[1]
  - Ignore les coûts sociaux (alignment, ownership, on-call), organisationnels (frontières d'équipe, funding) et opérationnels (run, observabilité, feedback loop).[1]

***

Si tu veux, on peut enchaîner sur une lecture “cloud/IA” de ces principes, par exemple : comment les appliquer à un programme RAG/agentique sur un hyperscaler en gardant une approche très FinOPS.

=== OAuth 2.0 et OpenID Connect (OIDC)

==== OAuth 2.0 : protocole ou framework ?

-> *OAuth 2.0 est-il un framework ou un protocole ? Explique la différence entre les 2*

.Gemini
--
OAuth 2.0 est un protocole, non un framework.

* *Qu'est-ce qu'un protocole ?*

	** Un protocole, en informatique, définit un *ensemble de règles et de conventions régissant la communication entre différents systèmes*. +
	Il spécifie le format des messages, la séquence des opérations et les actions à entreprendre en réponse à certaines conditions. +
	En d'autres termes, c'est un langage commun que les systèmes utilisent pour se "parler" entre eux.

	** Exemple : Le *protocole HTTP* définit les règles pour la communication entre un navigateur web et un serveur web.

* *Qu'est-ce qu'un framework ?*

	** Un framework, quant à lui, est une *structure de base réutilisable qui fournit une abstraction de certaines fonctionnalités communes d'une application*. +
	Il offre un ensemble d'outils, de bibliothèques et de conventions pour accélérer le développement d'applications. +
	Un framework ne se soucie pas de la communication entre les systèmes, mais plutôt de *la manière dont une application est construite à l'intérieur*.

	** Exemple : Le *framework Django* pour Python fournit un ensemble d'outils pour développer des applications web rapidement, en s'occupant de la gestion des URL, du modèle-vue-contrôleur, de la base de données, etc.

* *Pourquoi OAuth 2.0 est un protocole ?*

	** OAuth 2.0 définit un ensemble de règles précises pour l'autorisation d'accès à des ressources. Il spécifie comment une application peut demander à un utilisateur l'autorisation d'accéder à ses données sur un autre service (comme Google ou Facebook). Ces règles sont indépendantes de toute technologie particulière, et peuvent être implémentées dans n'importe quel langage de programmation.

En résumé :

	* OAuth 2.0 est un protocole qui définit comment les applications peuvent s'authentifier les unes les autres.
	* Un framework fournit un ensemble d'outils pour construire des applications.

Pour mieux comprendre la différence, imaginez que vous construisez une maison:

	* *Le protocole serait l'ensemble des normes de construction* (dimensions des briques, normes électriques, etc.). Il définit comment les différents éléments de la maison doivent être assemblés.
	* *Le framework serait un ensemble d'outils et de matériaux pré-fabriqués* (kits de cuisine, planchers préfabriqués, etc.) qui vous permettent de construire la maison plus rapidement.

IMPORTANT: -> En conclusion, OAuth 2.0 est un *protocole qui établit les règles de l'autorisation*, tandis qu'un *framework vous aide à mettre en œuvre ces règles dans une application spécifique*.
--

==== Différences entre OAuth 2.0 et OIDC

.Attention aux éléments de langage empruntés à OIDC et qui complique la compréhension...
[NOTE]
====
Dans le schéma précédent, on parle d'"IdP" (Identity Provider) pour le serveur validant les credentials de l'utilisateur. +
Il serait plus correct de parler d'AS (Authorization Server) pour ce serveur étant donné que OAuth est un protocole de délégation d'autorisation et pas d'identification. +
-> C'est OIDC (OpenID Connect) qui va apporter la surcouche liée à l'authentification (et NON l'autorisation) des utilisateurs.

Pour rappel, *OpenID Connect* (OIDC) étend OAuth pour fournir un *protocole d'authentification*.
====

*OAuth 2.0* :

	* *Focus sur l'autorisation* : Le protocole OAuth 2.0 se concentre principalement sur la délégation d'autorisation. Il permet à une application cliente (par exemple, une application mobile) d'obtenir un accès limité aux ressources d'un utilisateur sur un serveur de ressources (resource server), sans exposer les informations d'identification de l'utilisateur à l'application cliente.
	* *Authorization Server* (AS) : C'est le composant central d'OAuth 2.0. Il est responsable de l'émission des tokens d'accès et d'actualisation, et de la validation des demandes d'autorisation. Il ne se préoccupe pas de l'authentification de l'utilisateur en tant que telle.

*OIDC* :

	* *Extension d'OAuth 2.0* : OpenID Connect (OIDC) est une couche d'identité construite sur OAuth 2.0. Il ajoute des fonctionnalités d'authentification à OAuth 2.0, permettant ainsi aux applications clientes de vérifier l'identité de l'utilisateur.
	* *Identity Provider* (IdP) : Dans OIDC, l'Authorization Server est souvent appelé Identity Provider (IdP). Cela reflète le fait que l'IdP ne se contente pas d'autoriser l'accès aux ressources, mais il authentifie également l'utilisateur et fournit des informations sur son identité (claims) à l'application cliente.

En résumé :

	* OAuth 2.0 se concentre sur l'autorisation et utilise un Authorization Server (AS).
	* OIDC étend OAuth 2.0 pour inclure l'authentification et introduit le concept d'Identity Provider (IdP).

=== Pyramide des tests

* URL de l'article ByteByteGo (2025/08/30) : https://blog.bytebytego.com/i/172292074/the-testing-pyramid

image:20250830_ByteByteGo_pyramide-tests_01.jpg[]

Testing is the backbone of reliable software. The Testing Pyramid is a widely accepted strategy for structuring tests into three key layers:

	* *Unit Tests* : These are the foundation of the pyramid. Unit tests are fast, isolated, and low-cost to write and maintain. They test individual functions, methods, or components.

	* *Integration Tests* : These tests validate interactions between components, such as APIs, databases, and external services. They are slower than unit tests and require more setup.

	* *E2E Tests* : These simulate real user flows from start to finish across the full system. They are expensive to write and maintain and tend to be slow to execute.

-> As you go up the pyramid, the cost of test development, execution, and maintenance increases.

=== Session, Cookie, JWT, Token, SSO, and OAuth 2.0 Explained in One Diagram

* Super article de ByteByteGo : https://blog.bytebytego.com/i/155600813/session-cookie-jwt-token-sso-and-oauth-explained-in-one-diagram

image:20250127_ByteByteGo_Session-JWT-token-SSO-Auth-2.0_01.jpg[]

When you login to a website, your identity needs to be managed. Here is how different solutions work :

	* *Session* : The server stores your identity and gives the browser a session ID cookie. This allows the server to track login state. But cookies don't work well across devices.
	* *Token* : Your identity is encoded into a token sent to the browser. The browser sends this token on future requests for authentication. No server session storage is required. But tokens need encryption/decryption.
	* *JWT* : JSON Web Tokens standardize identity tokens using digital signatures for trust. The signature is contained in the token so no server session is needed.
	* *SSO* : Single Sign On uses a central authentication service. This allows a single login to work across multiple sites.
	* *OAuth2* : Allows limited access to your data on one site by another site, without giving away passwords.
	* *QR Code* : Encodes a random token into a QR code for mobile login. Scanning the code logs you in without typing a password.

.Produit vs Projet
--
Un *produit* est une offre matérielle ou immatérielle qui répond à un besoin ou satisfait une envie. +
Il est le résultat de la stratégie commerciale d'une entreprise et doit être conçu, développé et géré afin d'apporter de la valeur au client. Il est ensuite mis au catalogue, et est régulièrement mis à jour dans le cadre de son cycle de vie - jusqu'à ce qu'il soit retiré du marché - en fonction d'une roadmap établie pour répondre aux besoins des clients, qui évoluent au fil du temps. +
Le produit vise un objectif, et chaque itération s'en rapprochera.

De son côté, un *projet* est un effort temporaire qui a pour but de répondre à un besoin unique : il s'agit de créer un livrable spécifique, pour une date précise et un budget fixé à l'avance. Ce qui ne laisse pas de place à l'imprévu, et va donc à l'encontre des principes agiles ; cette façon de faire est une source évidente de frustration lorsque cet imprévu arrive (ce qu'il fait immanquablement).

* *MVP vs MLP* : Minimum Valuable Product vs Minimum Lovable Product

    ** Un MVP est une version d'un produit qui possède l'ensemble minimal de fonctionnalités nécessaires pour être utilisable par les clients.
    ** Un MLP, en revanche, est une version d'un produit qui possède l'ensemble minimum de fonctionnalités nécessaires pour être aimée des clients.

    ** En résumé, la principale différence entre MVP et MLP est l'accent mis sur le retour d'information des clients et l'engagement émotionnel. +
    Un MVP se concentre sur la collecte de commentaires et l'itération sur le produit, tandis qu'un MLP se concentre sur la création d'un lien émotionnel positif avec les clients du produit.

        *** *Cloud-native* : +
        Applications construites à l'aide de containers, serverless (fonctions déclenchables avec des événements) ou autre capacités PaaS
        *** *Headless* : +
        Headless signifie que l'application n'a pas d'interface utilisateur, et qu'on y accède et la *contrôle exclusivement par le biais d'API*. Cette approche permet une plus grande flexibilité et personnalisation, car l'interface utilisateur peut être construite et modifiée indépendamment de l'application sous-jacente.

* *REST vs GraphQL*

    ** REST : 
        *** différents points d'accès (endpoints) selon les données que le producteur d'API va mettre à disposition
        *** Erreurs et validation des données : Dans une API REST, le serveur renvoie généralement des codes d'erreur HTTP pour indiquer les échecs, comme 404 pour "non trouvé" ou 500 pour "erreur de serveur".
    ** GraphQL : 
        *** un seul point d'accès permet d'accéder à l'ensemble de la donnée, et c'est le consommateur qui choisira celle qu'il souhaite récupérer.
        *** Erreurs et validation des données : Dans une API GraphQL, le serveur peut renvoyer des messages d'erreur détaillés avec les données, ce qui facilite la gestion et le débogage des problèmes par le client.
    ** Conclusion : *GraphQL* peut être un bon choix pour construire des API qui doivent être *flexibles* et *personnalisables*, tandis que *REST* peut être un bon choix pour les API qui suivent un *design plus standard et établi*.
